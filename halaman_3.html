Choose storage separately from orchestration. A scheduler does not decide how facts should be modeled, and a transformation framework does not guarantee source completeness.

Before adopting a warehouse, measure query duration, concurrency, freshness requirements, and interference with application traffic. Keep the review focused on observable outcomes. For example:

●     Can a failed batch be replayed without changing correct totals?

●     How are conflicting source versions detected?

●     Which reports change when an old order is updated?

●     Who owns freshness alerts and recovery?

A dashboard total needs context about when its underlying data became usable.

Track the latest successful ingestion, transformation, and validation separately. A recent extraction timestamp does not prove that downstream models finished building.

Likewise, a quiet source can make an event timestamp look old even when ingestion is healthy. Combine source activity with pipeline execution metadata before deciding that the data is stale.

Define the serving behavior when checks fail. You might keep the last validated result available with a visible freshness warning rather than replace it with an unverified total. #48. I’m Baffled by Oppo’s Find X10 Pro Max, but I Love It Anyway

Our gifting experts are obsessively searching for holiday gifts that are unique, thoughtful and suitable for any budget.

Our expert, award-winning staff selects the products we cover and rigorously researches and tests our top picks. If you buy through our links, we may earn a commission.

Oppo launched two excellent phones within six months of each other. I’m confused, but maybe you can figure it out.

Editor at Large; Lead Photographer, Europe

Editor at Large; Lead Photographer, Europe

It feels a bit weird to be writing about Oppo’s new Find X10 Pro Max flagship phone. I only reviewed the company’s last flagship, the Find X9 Ultra, back in June. But as the larger number in the name suggests, the X10 Pro Max is the first of Oppo’s next generation of Android phones, packing a whole suite of new tech, from fancy new camera sensors to the new MediaTek Dimensity 9600 Pro chip.

I’ve been testing it for the past week or so, and there’s no question it’s a powerhouse phone that’s well worthy of its flagship title. But I said much the same about the Find X9 Ultra, with both phones boasting incredible Hasselblad-branded camera setups and potent processors. Both also make use of detachable telephoto zoom lenses for shooting long-distance photos.

It’s not that I have any problem with the X10 Pro Max so far — it’s great in every respect — it’s just that I don’t know why it needs to exist so soon after the X9 Ultra debuted. I’ve already been quite vocal about companies launching new flagships every year and the X10 Pro Max doesn’t seem to have moved the story on all that much since the X9 Ultra. And at a starting price of £1,499 in the UK (roughly $2,010) the Pro Max costs roughly the same as the X9 Ultra, too. It does come with a “complimentary accessory” in the form of either the detachable telephoto lens or an Oppo smartwatch.

Between the Find X9 Pro launched last October and the X10 Pro Max seen today, there are clear upgrades across the board. But between the more recent Find X9 Ultra and the Find X10 Pro Max it’s less clear-cut. Right now, I can’t tell you which has the better camera — both the X10 Pro Max and the six-month-old X9 Ultra have awesome setups, and I’ve taken great photos with both.

The Ultra phones have traditionally stood apart from the Pro phones by having better screens, processors and camera systems. With the X10 Pro Max matching — or beating — the X9 Ultra’s performance across the board, I’m struggling to understand why you’d pick one over the other. Maybe this distinction will become clearer later.

Or for a more positive spin, I find myself in a situation where both these phones appear so equally superb that I can’t choose between them.

If you live in the US, this is something of a moot point. Oppo doesn’t officially sell its phones in your country, so you can’t buy either of them. If you’re still keen to know more about this phone, here’s what I like so far.

I’ve been impressed with the cameras on Oppo’s recent phones, and the Find X10 Pro Max is no exception. It echoes some of what I saw in the Find X9 Ultra (200-megapixel main and telephoto lenses), but it bumps the ultrawide to 200 megapixels and adds an interesting upgrade to its main camera sensor.

The main camera uses a Samsung Isocell HPC sensor with something called DeepPix technology. What this essentially does is allow for more light information to be captured, resulting in a dynamic range (the difference between the brightest and darkest parts of an image) of around 17 stops. That’s up there with professional cinema cameras, but it also sounds like similar technology to the LOFIC (lateral overflow integration capacitor) sensor seen in phones like the Leitzphone by Leica and Xiaomi and in the recent DJI Osmo Pocket 4P.

Because I’m neither an image sensor engineer nor a physicist, I can’t tell you exactly how these technologies differ — or if it really matters, as fundamentally they aim to achieve the same thing: better-looking images with more light information captured.

Technicalities of the sensor aside, I’ve been pleased with many of the images I’ve taken with the phone so far. Dynamic range is (perhaps unsurprisingly) excellent, with colors that look punchy yet natural in both tone and saturation.

While some images can look a bit overprocessed, with unnaturally lightened shadows, I think the phone gets the balance right better than many Android cameras. Oppo also says it’s taken a lighter-touch approach with artificial image sharpening, instead giving images a more natural appearance when it comes to fine details. I think this has worked for the most part, although I sometimes find it goes too far the other way, with some highlights having a noticeable haziness and lack of definition around them.

Like with the Find X9 Ultra, I found that some of my favorite shots were taken using the Master mode where I took manual control of settings, including white balance, and in some cases shot in DNG raw to apply my own edits in Adobe Lightroom.

There’s little color shift between the main and ultrawide lenses, and the 3x optical telephoto camera captures crisp details, with almost no noticeable drop in quality when you push the zoom to 6x by using digital cropping.

If you want to take the zoom even further, slap on the physical telephoto zoom lens to achieve an optical zoom up to 10x and a digital zoom up to a whopping 40x. I’ve used these lenses on the X9 Ultra and the X9 Pro before and they’re good fun, especially if you’re into wildlife photography and want to capture a bird off in the distance.

The quality isn’t great when you push it right to 40x, and the phone uses AI to upscale some of the details, but it’s far better than what you’d achieve with the phone by itself. I don’t know exactly how much the X10 Pro Max’s telephoto lens will cost, but keep in mind that the Hasselblad lens for the Find X9 Ultra was a princely $400 accessory.

The camera comes with extras like the Hasselblad XPAN mode for taking wide, narrow panoramic images, along with a new color filter tool that’s basically identical to the color and tone grid Apple uses in its Photographic Styles. Still, I’m not complaining — it works well and it’s easy to craft a more creative look for your image. I suspect Apple may not be thrilled at the similar interface.

I’m overall impressed with the camera on the Find 10 Pro Max. It’s more than capable of taking stunning images, especially if you’re into your zoomed-in shots. But I can’t say if it’s any better than the Find X9 Ultra, or even if it’s supposed to be. The new sensor technology should mean it’s the better camera, but the Find X9 Ultra has a second telephoto zoom camera, a longer telephoto accessory and it’s covered in Hasselblad branding and colors.

To understand the minute differences between their camera capabilities, I need time to put the two phones side-by-side. I also want to test it against the Leitzphone to see how the DeepPix sensor compares to the LOFIC one. The Leitzphone’s sensor is also physically larger, and the phone itself offers unique photography tricks like its continuous telephoto zoom, its physical settings wheel and its variety of Leica film profiles, all of which make it the camera phone to beat, in my opinion.

The Find X10 Pro Max is powered by the latest MediaTek Dimensity 9600 Pro chip, rather than a Qualcomm chip as you’ll find in the Find X9 Ultra. There are some differences in performance between the two processors, with the X10 Pro putting in better processing scores on Geekbench 7, while the Find X9 Ultra’s Qualcomm Snapdragon 8 Elite Gen 5 chip consistently outperforms on 3DMark’s graphics benchmark test.

In everyday use, the X10 Pro Max was capable of handling everything I could throw at it, from demanding games like Genshin Impact to editing images in Adobe Lightroom. I honestly can’t say I find the phone to be any more (or less) powerful than the X9 Ultra, so if you were hoping to choose between the phones on benchmark tests alone, then you’re out of luck.

What continues to bug me with Oppo’s phones is the needless amount of junk you’ll find preinstalled the first time you turn it on. There are third-party apps such as Temu, TikTok, ChatGPT and LinkedIn, and apps I’ve never heard of, including Bigo Live and iQiyi. Throw in the wealth of Oppo’s own apps, shopping services and theme stores, and the phone feels cluttered before you’ve even had a chance to download anything of your own.

This is nothing new, though — I leveraged the same criticism at the Find X9 Ultra, and indeed many other Android phones. Yes, you can uninstall any of the garbage you don’t want, but it irks me that these expensive phones feel ad-supported because of the casserole of nonsense clogging your app library.

The Find X10 Pro Max packs a whopping 8,000-mAh silicon-carbon battery, at least in my test version; some EU regions will have a slightly smaller 7,150-mAh battery. After an hour of our YouTube streaming rundown test, the phone had dropped from full to 98% remaining and by the third hour was only down to 89%.

That’s not bad at all, putting the phone in line with top performers like the Samsung Galaxy S26 Ultra although not quite troubling the epic stamina of the iPhone 18 Pro Max. It also didn’t quite beat the scores achieved by the Find X9 Ultra. Still, it’s a great effort and you should comfortably expect the phone to offer at least a full day of demanding use with enough spare to get you a fair way into day two.

The phone supports 80-watt wired fast charging which should make it extremely quick to put some juice back in the tank if you’re running short before heading outside. Though you’ll need to get a compatible fast charger. Oppo also reckons the battery is optimized for longevity, promising the battery capacity will only drop to 80% after five years.

While I obviously haven’t been able to test this, I’m pleased that there’s a focus on longer-lasting hardware to keep your device going for longer. Oppo offers five years of software updates and six years of security updates, which is a step behind the seven years Google and Samsung offer, but I suppose it could be worse.

As I mentioned at the start, I find this phone’s existence confusing. It’s a camera powerhouse, but it comes right off the back of another Oppo camera powerhouse — there’s a huge amount of overlap in what these phones offer and who might be interested in buying them. They’re both superb, no question about that, but it’s like inviting two Michelin Star chefs to cook the same meal for your party — there might be subtle differences that mean some like one over another, but at the end of the day, why have both?

I rarely wish for companies to offer less in their product lineups, but in this instance I feel Oppo might have been wise to hold back some of its camera innovations — especially the new sensor tech. Instead, the Find X10 Pro Max could have been more focused on general lifestyle, productivity and gaming, giving the Find X9 Ultra a bit more breathing room.

Then, after Spring next year, the company could launch the Find X10 Ultra, packed with incredible camera tech that totally changes the game and makes it feel fresh and exciting. Instead, the X10 Pro Max feels so close to its six-month-old sibling that I’m struggling to work out which one is actually better and, more importantly, why both need to exist at the same time.

Early adopters who shelled out the high price for the Find X9 Ultra specifically for the camera performance may well feel a little cheated that the company has so quickly launched a phone with brand-new, superior image sensor technology. It feels like Oppo is at risk of diluting its impact, cannibalizing sales of its own products and potentially even alienating existing customers.

But company strategy aside, the X10 Pro Max is excellent, offering everything you’d need from a flagship phone right now. It’s got enough power for any of your daily tasks and the camera is well-equipped to capture your world as you see it. How it compares to the competition remains to be seen.

#49. Trust Docker for the agents you don’t

Secure, minimal container images for every team, free with enterprise features, if needed.

Cloud Sandboxes, open Kits, and a developer community building the next generation of AI software

Docker Cloud Sandboxes are here. At WeAreDevelopers World Congress North America, we launched a way for developers to start agent work in a safe way on their laptop, move to the same microVM environment on Docker-managed cloud compute, and bring the results back. Longer tasks can keep running, even after you close your laptop.

That launch reflects a bigger ambition. We want developers to be able to give agents useful work with confidence in the systems around them. That means a place for the agent to run, clear limits on what it can access, and a way to inspect what happened. It also means keeping the freedom to choose the agent and model that fit the job.

We brought that message to San Jose with Cloud Sandboxes, the open Sandbox Kit specification, and a commitment to bring the spec to the Cloud Native Computing Foundation (CNCF). Three mainstage talks explored what trust requires in practice. Four workshops gave developers time with the tools. Across the Docker Pavilion and booth, customers, partners, and community members brought their own experience and questions into the discussion.

A year after announcing our partnership to bring WeAreDevelopers to North America, it was exciting to join more than 10,000 developers, AI builders, and technology leaders at the inaugural event, September 23-25. Here is what we shared, and where developers can get started.

An agent working through a large refactor or migration may need more time than you want to keep a laptop open. Running several tasks at once can put pressure on local resources, too. Cloud Sandboxes gives those tasks somewhere else to run.

Each sandbox is an isolated microVM, a small virtual machine with its own kernel and Docker daemon. The agent can install dependencies, build applications, and run containers inside that environment. With Cloud Sandboxes, Docker supplies the compute, and developers use sbx, the same command-line tool they use for local sandboxes.

The workflow starts wherever the developer needs it to. Begin locally, move the sandbox’s filesystem to the cloud for a longer run, and bring it back when it is time to review the results. The same reusable agent packages, called Kits, work in both environments. Local and cloud credentials and policies are configured separately, so the access granted in each environment remains an explicit decision.

Cloud Sandboxes are available now, with compute billed by the second. For developers, that opens up a useful choice: keep interactive work on the laptop and give longer agent tasks their own capacity. It makes the move from local experimentation to sustained agent work a practical part of the development workflow.

In his opening keynote, Docker President and COO Mark Cavage explained why giving agents more freedom also requires a stronger foundation. He described four requirements for an agent factory: containment, control, choice, and capacity. Teams need to know where agents can act, see and stop their activity, choose their models and tools, and run work beyond a single laptop.

The keynote included a clear example of what can go wrong. An agent running in a container with the host Docker socket mounted found a way to read a secret on the host. It had not discovered a new vulnerability. It was using access the configuration had given it.

Docker Sandboxes puts a microVM boundary around the agent. In a subsequent demonstration, the same attempt to reach the host through the Docker socket failed inside the sandbox. Containers still do the job of packaging and running applications; the sandbox gives the agent building those applications an execution boundary of its own.

This is what we mean by trust Docker for the agents you don’t. The infrastructure enforces the boundary, even when an agent chooses an unexpected course of action. Developers can decide how much access to grant and retain responsibility for the work that ships.

Cavage also addressed the limits of those controls. Blocking an unapproved network destination is different from recognizing that an otherwise permitted email is going to the wrong customer. Narrow permissions, such as allowing an agent to read and draft messages without letting it send them, remain an essential part of using agents responsibly. There is still work to do on whether an action matches the user’s intent, and we should be clear about that.

Once an agent has a place to run, the next question is what belongs in that environment. Which tools does it need? Which services may it reach? What credentials and storage should be available?

The new Docker Sandbox Kit specification puts those requirements in an artifact teams can share and review. A Kit is an OCI image containing the agent and its tools, together with declarations of the access it needs. It works with familiar image tooling: teams can build, push, pull, scan, and pin it by digest.

That makes an environment easier to reproduce, and it makes changes to its requested permissions visible. If a Kit asks for another network destination or credential, reviewers can see that change alongside the rest of the package. The runtime decides which requests to grant and enforces the resulting policy outside the agent.

We published the specification under Apache 2.0 and committed to bringing it to the CNCF for neutral governance. Docker Sandboxes is the first runtime to implement it. Opening the format gives other runtimes a specification they can adopt and developers a common way to describe an agent environment.

Nous Research joined Cavage onstage with Hermes, its open-source agent, as a launch partner. Packaging an independently developed agent as a Kit demonstrated the choice we want developers to have: use the agent that fits the work, with an environment and controls the team can understand.

Docker CTO Tushar Jain’s keynote, “Govern the Runtime, Not the Agent,” took the discussion to the team level. Organizations use different models and agent tools. Governing each tool separately makes it harder to maintain a consistent policy and see the full picture of agent activity.

Tushar made the case for a common runtime layer that can govern execution, tools, credentials, permissions, and spend. His demo supplied a concrete example: an agent’s request to delete a GitHub repository was blocked by a default-deny rule and returned HTTP 403. Enforcement came from the runtime. In the Q&A, he described team-specific policies that can give a finance user and a developer different access to the same agent, while acknowledging that agent identity remains an open industry challenge.

Docker CISO Mark Lechner connected those ideas to security in his keynote, “One Boundary for the Agentic Era”. His talk connected those runtime controls to the software supply chain. An agent consumes dependencies and tools, then creates code that a team has to review and ship. Lechner showed how a Kit manifest describes the agent’s requested access, and how a proxy can use a credential without exposing the raw API key inside the sandbox.

Managing those capabilities as code gives security teams something concrete to review. They can inspect the environment an agent receives and compare its permissions with the activity recorded during a task. Across the three talks, the common goal was to make greater agent autonomy something teams can govern.

Prediction-market operators cannot advertise through Google Ads to residents of Connecticut, Michigan, Nevada, New York or Ohio, as disputes over sports-related event contracts continue in state and federal courts. CDC Gaming reported that the restriction affects Kalshi and other operators.

The five-state list creates an advertising barrier even as the underlying legal questions remain unsettled. Google’s policy sets conditions for where these companies can advertise, separate from the cases over whether states can stop them from offering contracts.

Google added a section on prediction markets to its main Google Ads policies document in the week before CDC Gaming published its report. The rules cover platforms that list, or provide customers access to, exchange-listed contracts tied to economics, sports or current events.

To advertise in an eligible location, a provider must hold the applicable local financial, commodities or gaming licences, comply with local laws and Google’s ad policies, and receive Google’s certification and approval. The company also requires advertisers to check the rules in each location they target.

Those conditions apply alongside the state exclusions: Connecticut, Michigan, Nevada, New York and Ohio. CDC Gaming reported that sports-event contracts are not available in Michigan or Nevada, a distinction from the wider advertising restriction, which covers prediction-market products.

CDC Gaming said each of the five states has sued prediction-market operators in an effort to block them from operating within its jurisdiction. Connecticut’s action against Kalshi is one example of the conflict over whether sports contracts fall under federal commodities regulation or state gambling rules, a dispute also reflected in Connecticut’s challenge to Kalshi’s sports contracts.

Operators have also challenged state enforcement. Underdog sued Tennessee, its attorney general and the Tennessee Sports Wagering Council after receiving a cease-and-desist order over sports-event contracts. The company’s position is that the CFTC regulates its event contracts and that federal oversight exempts them from the state’s gambling laws. Underdog has sued seven states over efforts to stop its sports-event contracts: Washington, Connecticut, Massachusetts, New Mexico, Ohio, Wisconsin and Tennessee. The arguments remain claims by the company, not a resolution of the broader regulatory dispute.

The competing approaches to federal and state oversight of prediction markets have left operators facing both legal challenges and location-specific advertising limits. The technologies and specific bands upon which cellular networks rely differ from country to country. While models described as “global” and even specifically UK or European models are likely to work in the US, they may not support all the bands your carrier uses. Missing LTE or 5G bands can mean patchy service or even relegate you to 3G. Chinese and other country-specific models will almost certainly lack some common US bands and may not work on some carrier networks.

You will often find this information in the listing or aggregated on websites like Kimovil, but I recommend checking directly with the manufacturer and your carrier.

Depending on where you buy, importing a phone can lead to customs charges and add a significant expense to the overall cost. Do your research and factor in any extra fees before you buy.

It is common for phones released only in China to ship without any Google services, including the Google Play Store. Many Chinese manufacturers have their own app stores or preinstall third-party app stores for the Chinese market. Sometimes it's a simple case of checking a box to unlock and download Google services, but it’s not always so easy.

#64. From Dockerfile to Kit: the Docker Sandboxes Kit Specification

Secure, minimal container images for every team, free with enterprise features, if needed.

Agents need containment, and a sandbox is only half of it. Something still has to say which agent runs there, what it gets, and what it may touch. That is a Kit: an ordinary OCI image, so the answer travels with the agent and means the same thing on any conforming runtime. Today we published the Docker Sandbox Kit Specification v3, open source under Apache 2.0 at docker/sandbox-kit-spec. Here is why I wrote it.

I run a lot of agents. They write code, run tests, install dependencies, call APIs, and work on infrastructure while I do something else. None of it happens without access, so I grant it one piece at a time: a bind mount, a token with broader scope than the task needs, a firewall rule that was quicker to open than to narrow. Each grant is reasonable on its own. Together they take back the isolation I was relying on, and none needed an exploit. The holes are configuration, added on purpose, usually by me.

I am worse at taking any of it back, and I could not reproduce the grants my setup depends on. No file records them. They live in shell history, dashboards, and my memory. I cannot hand that to a colleague or diff it against last week.

A container packages applications. It shares the host kernel and uses namespaces and cgroups to give one fixed workload its own view of the filesystem, network, and processes. That is the right tool for software that runs, does its job, and touches only what it was handed.

An agent, however, is a probabilistic actor. It decides what to do next and then does it, to my filesystem, network, credentials, and cloud account. It will install a package that needs root, open a port nobody planned for, and try the next thing when the first is blocked. A container was not built for that: the boundary is the same kernel the actor is probing.

A Docker Sandbox is a microVM with its own kernel, so the boundary sits below anything the model can reach or rewrite. Inside one I can hand an agent root and let it loose, because the damage stops at the sandbox boundary. The sandbox is what lets me run an agent with the safeties off.

But an empty sandbox is not an environment. Something still has to say which agent runs, which tools and MCP servers it gets, which skills and instructions shape it, and exactly what it may touch.

A Dockerfile answers everything about the software itself: how it is built, what gets packaged, how it starts. It was never standardized; OCI standardized the image it produces and how registries distribute it. What a Dockerfile does not describe is the outside: networks, credentials, volumes, tools, context. That half has lived in docker run flags, a Compose file, a CI config, and someone’s memory. Unversioned, unreviewable. A Kit writes it down with the content.

If you have used sbx, you have used Kits. This is the third version of the format, and the change that matters is that a Kit is now an ordinary OCI image rather than its own artifact: no media type, no sidecar file, nothing for a registry to learn. The manifest carries the declarations in one annotation, vnd.docker.sandbox.kit.descriptor; the layers carry the content.

A Kit therefore builds with docker buildx build, pulls with docker pull, gets scanned and signed by the tooling you already run, and works in a FROM. Pinning the digest pins content, declarations, and metadata together. The tooling and distribution path are free; the format is something you learn: a grammar, a page per capability type, provides and requires, kind: set.

Two kinds of Kit exist. A workload runs and supplies the root filesystem. A mixin is an overlay: a CLI with its network rule, a credential binding, context for an agent. You launch one workload and any number of mixins.

Read it as a permission slip. This Kit asks to reach GitHub and nowhere else, and for most of the API but not deletes under /repos/**, because deny wins. The token that can open a pull request cannot delete the repository. The credential is proxy-managed: a conforming runtime injects the real value into requests to the named domains, and inside the sandbox there is only a sentinel.

Two words carry weight: asks and conforming. A Kit grants itself nothing. Each entry is a request, and the host decides. A conforming runtime, one that implements the behaviour the specification describes, blocks hosts not on the list. Without one, the annotation is inert: an image and no enforcement. Docker Sandboxes is the first conforming runtime.

Everything a Kit needs goes through that one list, typed and versioned. Grants (network rules, credentials, volumes, ports, devices, skills paths) count toward “what may this Kit do”; entries that ask the runtime to act, like a lifecycle hook, do not. A required request the host cannot satisfy refuses the launch, rather than starting an agent with less authority than it declared, or more.

Container images never solved multiple inheritance: a Dockerfile stage has one FROM. Mixins are overlays ordered by the dependency graph the Kits declare through provides and requires, never by the order you typed the flags, so the same set always composes to the same image.

The resolver is strict on purpose. Every requires is satisfied from inside the set or resolution fails; nothing is fetched to cover a gap. Exactly one workload is allowed. Two Kits providing the same name fail rather than one silently shadowing the other (composing the Claude workload with the Claude mixin is the canonical mistake). Where Kits overlap, declarations reconcile: network rules union, hooks run in dependency order, guidance becomes one document, licenses union. Incompatible requests are an error, not a coin flip.

A kind: set descriptor names other Kits; publishing it runs the same coherence rules at build time and merges them into one ordinary Kit. An incoherent set fails at your build, not at someone else’s launch.

The Claude Code Kit in the repository declares the hosts it asks to reach, its credential, the volumes that persist between sessions, and its install and startup hooks. When the next version asks for another host or a second credential, that is a change in authority, not a software update, and it shows up in the pull request as added lines a human can refuse.

Review depends on somebody reading the diff, so the specification defines a second gate that does not. Every descriptor reduces to a normalized set of everything the host would have to grant; a runtime that gates updates records that set and compares the next version against it. A version inside what was granted may apply without asking. Any widening stops and asks, and removing a deny rule counts: if a later gh Kit dropped DELETE /repos/**, the runtime holds the upgrade. That is why the declarations had to live in the artifact, not beside it.

A Kit that stopped meaning anything when run somewhere else would be lock-in, not a trust boundary. So the grammar is normative, every capability type has its own page describing what a conforming runtime must implement, and types version independently (network-policy@1 and @2 both exist today). Two conformance suites ship with it: one judges whether an artifact is a conforming Kit, the other whether a runtime behaves as the pages say. Every normative statement is covered by a check or a written waiver.

Docker maintains the specification today, and it should not stay under a single vendor: a format for deciding what an agent may do is worth less if it belongs to whoever sells you the runtime. Docker Sandboxes will be a first-class implementation, not the only one. If a Kit you want cannot be expressed, or a runtime duty cannot be implemented as stated, open an issue.

That knowledge has lived in a Helm chart, a runbook, or a colleague. It is the same gap, less alarming when a web service gets it wrong. This specification is where any software writes down what it needs from the world around it; agents were the case urgent enough to have it built.

AI can accelerate implementation, but production readiness still requires engineering discipline.

Whether you are a developer using an AI coding assistant, a founder building a minimum viable product (MVP), or a team experimenting with vibe coding, this checklist will help you evaluate your application before releasing it to real users.

Vibe coding is an AI-assisted software development approach in which developers describe requirements in natural language and use AI tools to generate, modify, and debug code. Rather than manually writing every component, developers guide implementation through prompts, feedback, and iterative refinement.

This approach can accelerate prototyping, interface development, and repetitive programming tasks. However, generated code must still meet the same quality standards as conventionally written software.

Production readiness means an application has been tested and configured to operate reliably in its intended environment. It includes security, correctness, performance, maintainability, monitoring, and recovery.

Before deployment, evaluate the application across the following areas.

One common mistake in AI-assisted development is building features before defining what they should do.

A prompt such as "Build a project management dashboard" leaves important questions unanswered. Who can create projects? Can users access another person's tasks? What happens when a task is deleted? Which fields are mandatory? How should errors appear?

When these decisions are left to the AI, the implementation may reflect assumptions that do not match the product's requirements.

Core functionality: What must users be able to accomplish?

User roles: Who can view, create, edit, or delete information?

Data requirements: Which fields, relationships, and constraints are necessary?

Technical constraints: Which frameworks, databases, APIs, and hosting environments will be used?

Failure scenarios: What should happen when a request fails or data is invalid?

Acceptance criteria: What observable result proves that each feature works correctly?

For example, a task management application might have this requirement:

A user can view and modify only the tasks belonging to projects they are authorized to access. Unauthorized requests must be rejected without revealing protected data.

This is more useful than simply asking an AI tool to "add secure task management." It establishes a behavior that developers can implement and test.

Once the requirements are documented, ask the AI to implement one coherent feature at a time. Review the output before moving to the next feature.

This makes unexpected changes easier to identify and reduces the risk of introducing multiple interacting bugs through a single large generation.

Keep the requirements in a project document and update them whenever product decisions change. The specification should remain the reference point for both the developer and the AI coding assistant.

A functional interface can conceal serious implementation problems.

AI-generated code may contain duplicated logic, unnecessary dependencies, outdated API usage, incorrect assumptions about framework behavior, or abstractions that make future changes difficult. A successful build does not establish that the application behaves correctly.

Code review is therefore essential, even when an AI tool generates most of the implementation.

Start with the code responsible for important application behavior:

Check whether functions have clear responsibilities, whether data flows are understandable, and whether dependencies are actually needed.

For JavaScript and TypeScript projects, automated linting and type checking can catch many common mistakes. However, these tools cannot prove that business logic is correct or that permissions are enforced properly.

When reviewing a change, ask the AI to explain its implementation and identify its assumptions. Then verify those explanations against the actual code and relevant documentation.

If a function is difficult to understand, simplify it or request a clearer implementation. Code that nobody on the team can confidently maintain is a liability, regardless of how quickly it was generated.

Authentication answers the question, "Who is this user?" Authorization answers, "What is this user allowed to do?"

Both are necessary for applications that protect private information or restrict access to particular features.

An AI-generated application may implement a login screen and assume the security requirement is complete. In reality, hiding a dashboard element or redirecting an unauthenticated visitor does not prevent someone from calling a protected API directly.

Every sensitive operation should enforce the relevant permissions on the server or trusted backend.

For example, an application that allows users to view invoices should verify that the authenticated user is authorized to access the requested invoice. It should not rely solely on a user ID supplied by the browser.

Test both permitted and prohibited actions. A good security test confirms not only that the correct user can access a resource, but also that other users cannot.

For applications handling sensitive data, consider an independent security review before launch.

AI-generated applications often work well with expected inputs. Real users, however, submit incomplete forms, unexpected values, oversized files, malformed requests, and repeated actions.

Input validation and error handling help prevent these conditions from becoming application failures or security vulnerabilities.

Client-side validation improves the user experience, but it should not be the only line of defense. Requests can bypass browser validation entirely.

Validate incoming data on the server, using rules appropriate to each field and operation. Enforce database constraints where applicable, and use parameterized queries or safe ORM methods to prevent SQL injection.

For file uploads, validate file types, enforce size limits, and store files using a design that prevents unauthorized access. Do not assume a filename or content type supplied by the browser is trustworthy.

Users need understandable error messages. Developers need enough diagnostic information to investigate failures.

These requirements should be handled separately.

A user-facing response might say, "We couldn't save your changes. Please try again." An internal log can record a request identifier, the relevant operation, and a sanitized diagnostic message.

Avoid exposing stack traces, database credentials, internal configuration, access tokens, or sensitive records in production responses.

Also test what happens when external APIs time out, database connections fail, or required environment variables are missing.

A production-ready application should fail predictably, protect sensitive information, and provide a clear path to recovery.

Testing is particularly important in vibe coding because generated code can appear convincing even when it implements the wrong behavior.

Asking an AI tool to generate tests is useful, but those tests must be reviewed. A test suite can pass while validating incorrect assumptions or ignoring the application's most important failure cases.

Start with critical workflows rather than trying to test every minor interface detail.

For an e-commerce application, these workflows might include account creation, product selection, checkout, payment confirmation, and order retrieval. For a business dashboard, they might include importing records, updating a customer, assigning permissions, and generating a report.

Pay particular attention to boundary conditions.

What happens when a form is submitted twice? When an API returns an unexpected response? When a database operation fails halfway through a workflow? When two users update the same record simultaneously?

These scenarios often reveal problems that a successful demonstration will not.

For applications that process transactions, test idempotency where appropriate so that retries do not unintentionally create duplicate payments, orders, or records.

A web application can feel fast during development and become sluggish when it handles larger datasets, multiple concurrent users, or slower network connections.

AI-generated code should therefore be evaluated against realistic usage patterns.

Begin with the operations most likely to affect the user experience:

Use browser developer tools and server-side monitoring to identify actual bottlenecks before optimizing.

Database indexes can improve frequently used queries, while pagination can prevent interfaces from loading thousands of records at once. Caching can reduce repeated work when the data and consistency requirements allow it.

For public-facing websites, evaluate relevant Core Web Vitals and test performance on realistic devices and network conditions.

Avoid adding caching layers, complex abstractions, or performance libraries simply because an AI tool recommends them. Every additional component introduces maintenance costs and potential failure points.

Measure first, optimize the bottleneck, and measure again.

Generated applications frequently depend on third-party packages, API services, and environment-specific settings. Each dependency expands the application's maintenance and security responsibilities.

Before deployment, inspect the dependency manifest and lockfile. Remove unnecessary packages, verify that required packages exist, and review known vulnerabilities using appropriate dependency-scanning tools.

Keep frameworks and libraries updated according to a deliberate maintenance process rather than automatically accepting every suggested upgrade.

API keys, database passwords, signing secrets, and other credentials should not be embedded in client-side code or committed to a public repository.

Use environment variables or an appropriate secrets manager, depending on the deployment environment. Restrict credentials to the permissions they actually require, and rotate any secret that may have been exposed.

Remember that a variable included in a browser-delivered bundle is not secret simply because it was originally configured as an environment variable.

Also verify that development and production environments use the correct endpoints, database connections, authentication settings, and logging configuration.

A local application that works with unrestricted development credentials may behave very differently when deployed under production permissions.

Deployment should be a controlled process, not a final experiment performed after development is complete.

A repeatable deployment process reduces human error and helps teams identify which changes introduced a problem.

For projects that support it, establish a continuous integration and continuous deployment (CI/CD) pipeline with automated checks for:

Before launch, verify that you can restore the application to a known-good state.

This includes maintaining version control, documenting deployment steps, backing up important data, and testing restoration procedures. A backup is only useful if it can be restored successfully.

Database schema changes deserve particular attention. An incompatible migration can make an otherwise successful deployment unusable. For important applications, plan migrations so that application versions can coexist safely during rollout and rollback.

Also check how the application behaves when a deployment fails, a service becomes unavailable, or a configuration change introduces a regression.

A reliable release process should make failures easier to detect, contain, and recover from.

Testing happens before release and in controlled environments. Monitoring helps developers understand how the application behaves after real users begin using it.

Without monitoring, a deployment can appear successful while users encounter failed requests, slow pages, broken integrations, or database errors.

Set alerts for failures that require action. Avoid collecting unnecessary personal data in logs, and define retention and access policies appropriate to the application.

For AI-powered features, monitor additional factors such as model response failures, latency, token usage, and output quality. An application that depends on an external AI service must account for rate limits, changing model behavior, and provider outages.

Monitoring does not prevent every failure. It makes failures visible enough to investigate and resolve.

Before releasing an AI-generated web application, use the following checklist to assess whether the essentials are in place.

Requirements: Core features, user roles, constraints, and acceptance criteria are documented.

Code quality: Important code paths have been reviewed, and unnecessary dependencies have been removed.

Authentication: Identity and session handling are implemented appropriately.

Authorization: Protected resources and operations enforce server-side permissions.

Input validation: Requests, uploads, and database operations are protected by appropriate validation and constraints.

Error handling: Failures are handled predictably without exposing sensitive information.

Testing: Critical workflows, negative cases, and regression scenarios have been tested.

Security: Dependencies, secrets, configuration, and common vulnerability risks have been reviewed.

Performance: Important queries, endpoints, and user journeys have been evaluated under realistic conditions.

Deployment: Builds and releases follow a repeatable process with appropriate quality gates.

Recovery: Backups, restoration procedures, and rollback options have been considered and tested where applicable.

Monitoring: Errors, availability, and performance can be observed after release.

Not every application needs the same level of testing or operational complexity. A personal prototype has different requirements from a financial application or a multi-tenant SaaS product.

The important thing is to identify the risks associated with the intended use and address them before exposing real users or sensitive data.

A developer does not necessarily need an external review for every small experiment. However, an independent review becomes increasingly valuable when the application handles sensitive information, processes payments, supports multiple customer organizations, or implements complex permissions.

It is also worth considering when the original developer cannot explain important parts of the generated code or when repeated AI-generated changes have made the architecture difficult to understand.

A useful review should examine more than formatting and syntax. It should evaluate application behavior, data access, authentication, security controls, error handling, deployment configuration, and maintainability.

For teams using AI to accelerate development, the goal is not to eliminate AI-generated code. It is to make sure that the resulting software meets the quality standards expected of any application entering production.

Vibe coding changes how quickly developers can move from an idea to working software. It does not remove the need to understand requirements, validate behavior, protect data, test failure scenarios, and maintain the application after release.

The most reliable approach is to treat AI as a development accelerator within a disciplined engineering process. Define the requirements, review generated code, test critical workflows, enforce security controls, automate deployment checks, and monitor the application after launch.

Start with the checklist in this article and prioritize the controls that matter most to your application's risk profile. For a deeper look at the development process, read this guide to production-ready vibe coding.

The goal is not simply to build an application quickly. It is to build one that users can trust, developers can maintain, and businesses can depend on.

#66. AI Guardrails Aren’t Stopping Criminal Hackers

As AI adoption spreads among both malicious hackers and defenders, even relatively unsophisticated cybercriminals are incorporating agentic AI into their campaigns and getting around model safeguards, according to new details published on Wednesday about recent successful attacks by four different threat groups.

Researchers from the threat intelligence firm CrowdStrike looked at the AI infrastructure powering attacks perpetrated between May and August by four previously unreported groups—one that operates in Chinese, one in Spanish and English, one in Indonesian, and one in Russian. The former two exhibited sophisticated AI “harnesses,” the software that supports and guides a model to carry out tasks. The latter two showed less technical prowess, researchers found, but were still able to compromise multiple targets. All had left their AI infrastructure openly accessible on web servers, allowing the researchers to analyze their activity and which models they used—largely versions of Anthropic’s Claude as well as versions of the open-weight Deepseek models. All the actors devised ways to allow their campaigns to run autonomously over relatively long periods of time.

“You can leverage different models for different aspects in the operation. Model routing and selection is very important because it’s expensive and a lot of times would be overkill to use newer models,” says Adam Meyers, CrowdStrike's senior vice president of counter adversary work. The researchers observed the attackers using both open- and closed-weight models; in almost all cases, they were using older versions rather than working with frontier models. Meyers notes that doing as much as possible with older models is common in legitimate AI usage, too, as costs mount.

The attackers also used multiple models to take advantage of differences in the guardrails meant to prevent people from using AI to carry out digital attacks.

“The models don't all have equivalent guardrails and protections, even from one company,” Meyers says. He adds about the sophistication of the hacking campaigns overall that “these attacks are not using new exploits or novel vulnerabilities. They’re really just taking advantage of the speed and the volume that you can use AI for in conducting these operations targeting the bulk of security hygiene issues in a lot of these environments—things that were preventable but weren’t prevented.”

The researchers found that all four threat actors circumvented AI safeguards, often by convincing a model that the activity was all legitimate and authorized, often for penetration testing or other security evaluation. One method used by many of the groups involves adding files to an agent’s working directory to try to show that tasks are approved and authorized. The attackers also used traditional jailbreaking methods, crafting prompts and narratives framing their hacking as authorized and benign, and proactively addressing potential questions or concerns the models might raise. The more sophisticated actors were typically more strategic in their world-building, while the less sophisticated actors sometimes resorted to more crude and aggressive prompts that tried to bully the models into accepting that the activity was legitimate.

The Chinese-speaking actor also used what's known as a “run time patch,” in this case a tool known as ClawGod, to add functionality on top of Claude Code and attempt to remove the “CYBER_RISK_INSTRUCTION” from the Claude Code system prompt, an instruction directing Claude Code to only participate in authorized security testing, not abusive or destructive hacking.

The actor that worked in Spanish and English targeted Argentine health care entities and successfully compromised at least 15 organizations. CrowdStrike researchers see evidence that the actor stole credentials and medical records from at least one of these victims. The actor special built a penetration testing harness, the kind an organization would use to test its own infrastructure, to find and fix vulnerabilities. Using models including Claude Opus 4.5, Claude Haiku 4.5, and Deepseek V4 Pro, the group set up a full infrastructure for autonomous attacks involving a “Supervisor” Claude Code agent to direct the steps of an attack and an “Executor” agent to carry them out.

The attacker working in Chinese also built penetration testing harnesses to guide Claude Code in reconnaissance and then autonomously attack once a human had selected a course of action. The researchers found that the actor successfully compromised government targets in both Brazil and Colombia and also targeted private organizations in Brazil and the United States in a range of sectors that include biotech, healthcare, food and beverage, retail, technology, and travel.

According to the researchers, the Chinese-speaking actor primarily relied on Claude Opus 4.8, but also used other models including Claude Sonnet 4.6 and Deepseek Chat. The actor accessed Claude through an AI proxy service based in China but set up multiple fallbacks to other AI tools if Claude was not available through the proxy.

Anthropic did not provide comment ahead of publication, and Deepseek did not immediately respond to WIRED's requests for comment.

The researchers say that both the Russian-speaking actor, which seems to have been focused on financially motivated “e-crime,” and the Indonesian-speaking actor (the least sophisticated of the four) used more basic, publicly available skills and harnesses to carry out their attacks. But both were still successful at compromising targets. This included multiple Indonesian government domains, a Bangladeshi government domain, and some private-sector targets, in the case of the Indonesian-speaking actor.

“What we are seeing is humans are doing some of the initial probing in these situations and then they’re engaging the AI for the hacking at scale,” CrowdStrike’s Meyers says. “I find it interesting that even with agentic attacks with all of these capabilities, we could still see that there’s a human behind it and what they’re up to.”

#67. Native Model Authoring for Edge with LiteRT Tensor API

Shipping on-device AI means meeting tight latency and memory budgets on every device you target. The most common path for deploying models in production is converting a trained model, for example converting a PyTorch model with LiteRT Torch, and running it with the LiteRT runtime. This offers the quickest and most reliable route to production, and it's the path we recommend for most projects. Sometimes, though, developers want full control over how a network is represented and optimized to support new architectures or to try a new lowering logic without waiting for upstream framework updates.

For ultimate control, developers write computations manually in native C++ or shader languages. Apple's MLX made this code-first approach popular on Apple silicon, and llama.cpp showed how far tailored C++ implementations can take LLM inference. However, the level of control comes at a significant cost: implementations are tightly coupled to specific backends (such as Metal, OpenCL, or Vulkan) and must be rewritten for each new hardware target. Furthermore, managing zero-copy buffer interoperability and synchronization across CPU, GPU, and NPU, while gluing together pre-processing, inference, and post-processing, demands substantial manual engineering effort.

To solve the above challenges, we are excited to announce the release of the novel LiteRT Tensor API, a lightweight authoring layer in the LiteRT stack, designed to improve handcrafting models. It combines the flexibility of native authoring with cross-platform portability. You build the computation graph op by op in C++, choosing exactly which ops run and how they connect. The same graph can run through LiteRT on CPU, GPU (powered by open-source ML Drift) and NPU, or without model file or runtime directly on CPU through XNNPACK, so you don't rewrite it for each new hardware target. Model inference and pre/post-processing can be assembled with the same API and chained through shared accelerator buffers, so that data never round-trips through the CPU. Start with the conversion path, which remains the best default for most models. Reach for the Tensor API when you need low-level control over the graph or want the whole pipeline to run end to end on the accelerator.

The LiteRT Tensor API also serves as an ideal programmatic foundation for AI coding agents, providing structured primitives to generate, rewire, and tune model graphs automatically. In the rest of this post, we’ll dive into the design and walk through practical code examples showing how to author models from scratch.

A real app needs more than the neural network itself.
